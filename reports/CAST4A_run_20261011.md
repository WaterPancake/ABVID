## Diagnosis

To reproduce it, the site_0 population was rebuilt read-only and the failing sample
(`site_0:v14_joint:car:42:0000`) was regenerated twice in one process:

- The record, descriptors, planned entry and bundle metadata are **byte-identical** to
  the stored sample.
- The decoded waveform matches exactly: the maximum absolute difference is **0.0**.
- Only `waveform.wav` differs, and two regenerations a second apart also differ from
  each other.

A minimal check with soundfile 0.14.0 and libsndfile 1.2.2 locates the difference.
Writing the same float32 array twice as `WAV/FLOAT` produces files that differ in
**exactly one byte, offset 60**. That byte is the timestamp field of the `PEAK` chunk
libsndfile adds to float WAV files. The runner's `_checkpoint` compares raw payload
bytes on replay, so any replay that happens in a different second from the original
write fails.

**Conclusion:** the generated numerics are reproducible across processes. The failure
is a serialization defect in the pinned runner's replay comparison, not evidence about
CAST.

## Proposed correction (requires human review; not applied)

Following the runner's own failure policy, a corrected implementation must be a
**separately pinned execution revision** that preserves this attempt.

1. Serialize generated waveforms deterministically. Either store float32 `.npy`
   bytes, or write WAV with the `PEAK` chunk disabled
   (`SFC_SET_ADD_PEAK_CHUNK = false`). Alternatively, compare decoded samples plus
   metadata instead of raw container bytes.
2. Pin the revision as a new execution configuration with a new output directory.
   Its implementation and test hashes cover the changed runner module and a regression
   test that writes, sleeps past a second boundary and replays.
3. Reuse the 1,864 completed parent bundles through the existing same-parent rules.
   Regenerate the 27,000 samples. Their numerics are expected to match, and this can be
   checked against the v1 decoded waveforms. Then run the held-descriptor scoring.

Steps 1–2 modify pinned CAST-4A code and its test pins. Under AGENTS.md they need your
review and a human-only harness-baseline refresh, so this session did not apply them.
